# Codex · 2026-08-19 · 초기 스캐폴드 공개 및 Phase 0 명단 검증 보강

**주요 파일**:
`README.md`,
`docs/IMPLEMENTATION.md`,
`docs/phase0-verification.md`,
`supabase/migrations/`,
`supabase/seed/`,
`data/`,
`assets/`

## 배경

공개 GitHub 저장소가 비어 있고 로컬 스캐폴드에도 Git 이력이 없었다. 또한 기존 Phase 0 문서는 남의 길드 레이드 기록 권한만 검사해, 공격하지 않은 길드원을 판별하는 데 필요한 `GetGuildMembers` 명단 권한을 별도로 확인할 수 없었다. 사용자는 첨부 스캐폴드와 구현 명세를 저장소에 게시하고 이 검증 절차를 보강해 달라고 요청했다.

## 기존 → 변경 후

| 구분 | 기존 | 변경 후 | 변경 이유 |
|---|---|---|---|
| 저장소 기반 | 원격 저장소는 빈 상태였고 로컬 파일 478개에는 Git 이력이 없었음 | 첨부 ZIP과 해시 대조한 DB·데이터·자산·문서 스캐폴드와 구현 명세를 초기 커밋 대상으로 구성 | 이후 Phase 작업이 동일한 기준 소스와 문서에서 이어지도록 하기 위해 |
| Phase 0 권한 검증 | `GetUnionRaidDataOfGuildSeason`으로 남의 길드 레이드 기록만 검사 | `GetGuildMembers` 명단 요청, 우리 길드 대조군, 기록·명단 조합별 경로 A/A′/B 판정을 함께 기록 | 명단 권한이 막힐 때 미참여 `0/3` 판정만 불완전해지는 상황을 별도로 구분하기 위해 |
| 닉네임과 신원 | 명단 응답의 닉네임 출처와 닉네임 변경 시 연결 기준이 Phase 0 문서에 드러나지 않음 | 현재 명단과 공격 시점 기록에서 닉네임을 자동 수집하고, 동일인은 변경되지 않는 `openid`로 연결한다고 명시 | 닉네임 수동 입력을 없애면서 닉네임 변경에도 기록이 끊기지 않도록 하기 위해 |
| 공개 샘플 안전성 | 샘플 저장 전 쿠키 제거만 강조 | 쿠키와 함께 실제 `openid`와 닉네임도 익명화하도록 명시 | 공개 저장소에 인증정보나 사용자 식별정보가 포함되는 위험을 낮추기 위해 |

## 상세 변경

- ZIP 내부 파일과 동일한 `docs/IMPLEMENTATION.md`를 추가하고 README 디렉터리 안내에서 연결했다.
- `docs/phase0-verification.md`의 기존 검증을 1-A 레이드 기록과 1-B 길드원 명단으로 분리했다.
- `GetGuildMembers` 요청 스니펫, 우리 길드 대조군, 응답 위치 후보(`data.items` 또는 `items`)를 기록했다.
- 1-A/1-B 결과에 따라 정확한 미참여 체크, 제한된 미참여 체크, 길드별 최초 연결로 나뉘는 설계 분기를 문서화했다.
- README의 미검증 전제를 레이드 기록 권한과 전체 명단 권한 두 가지로 정정했다.
- Phase 1~5 구현, 실제 BlablaLink 로그인 세션을 사용한 Phase 0 실행, Supabase/Vercel 배포는 이번 작업에 포함하지 않았다.

## 영향 및 호환성

- DB 스키마, 환경변수, 저장 데이터 형식, 외부 API 요청 계약의 런타임 동작은 변경하지 않았다.
- 새 마이그레이션이나 사용자 데이터 변환은 필요하지 않다.
- 공개 저장소에 실제 쿠키, 토큰, `openid`, 닉네임 샘플을 추가하지 않았다.
- 현재 결과물은 실행 가능한 Next.js 앱이나 Edge Function이 아니라 DB·시드·자산·문서 스캐폴드다.

## 확인

- 첨부 ZIP 479개 파일과 작업 폴더를 상대 경로·SHA-256으로 대조해, 의도한 문서 변경 외 누락이 없음을 확인했다.
- `docs/IMPLEMENTATION.md`가 별도 첨부 파일 및 ZIP 내부 파일과 동일한 SHA-256(`4A061398…A0A7B`)임을 확인했다.
- `python -B scripts/generate_seed.py`를 연속 실행해 196/45/5행을 생성하고 두 번째 실행에서 바이트 단위 멱등성을 확인했다.
- JSON 원본을 파싱해 보스 9시즌·45행, 계수 1시즌·5행, 리소스 매핑 196개를 확인했다.
- 니케 이미지 397개와 보스 이미지 65개, 니케 CSV 196행을 확인했다.
- 고신뢰 비밀값 패턴 검사에서 실제 키·토큰·개인키를 발견하지 않았다.

# Codex · 2026-08-19 · 실행 가능한 대시보드와 안전한 DB 기반 구현

`package.json`,
`src/app/`,
`src/components/`,
`src/lib/`,
`public/`,
`supabase/config.toml`,
`supabase/migrations/20260819000300_permissions_and_view_fixes.sql`,

`supabase/migrations/20260819000500_roster_and_usage_scope.sql`,

`docs/phase0-console.js`,
`docs/operations.md`,

## 배경

초기 저장소에는 DB·시드·자산·문서만 있고 실행 가능한 웹앱, 데이터 접근 계층, 운영자 화면, DB 권한 회귀 테스트가 없었다. Phase 0의 실제 BlablaLink 응답과 배포 자격증명이 없는 상태에서도 구현 명세와 충돌하지 않는 로컬 범위를 먼저 완성하고, 사용자가 복제 직후 실행 방법과 아직 연결되지 않은 범위를 구분할 수 있어야 했다.

## 기존 → 변경 후

| 구분 | 기존 | 변경 후 | 변경 이유 |
|---|---|---|---|
| 웹 실행 | 정적 목업만 있고 `package.json`과 앱 라우트가 없었음 | Next.js 대시보드, 랜딩, 개요·조합·추이 탭, 동적 OG와 PWA 기본 구성을 추가 | 실제 화면과 반응형 흐름을 로컬에서 검증할 수 있게 하기 위해 |
| 데이터 계층 | 화면과 연결된 조회 계층 및 일관된 데모 데이터가 없었음 | 환경변수 미설정 시 파생형 익명 샘플, 완전 설정 시 Supabase 조회, 불완전 설정·조회 실패 시 명시적 오류를 제공 | 데모가 실제 장애를 숨기지 않으면서 바로 실행되게 하기 위해 |

| Day별 사용률·보스 딜 | 니케 사용률이 일반/하드 데이터를 섞고, 보스 딜은 조합이 있는 공격만 역산했음 | 사용률을 Day·난이도로 분리하고 보스 딜은 선택 Day의 원본 공격 전체에서 집계 | 선택한 기간과 화면 수치를 일치시키고 빈 스쿼드 공격도 누락하지 않기 위해 |

## 상세 변경

- 5개 서버 지역과 유니온 ID 검증, 최근 조회 기록, 라이트·다크 테마를 갖춘 랜딩 화면을 구현했다.
- 32명·96장 중 87장 사용이라는 동일 공격 원장에서 순위, 미참여, 보스, 조합, 니케 사용률과 시즌 추이를 파생하는 샘플 모델을 추가했다.
- Supabase 환경변수 두 개를 쌍으로 검증하고, 실제 조회 오류가 샘플 모드로 자동 전환되지 않도록 분리했다.
- 분석 뷰의 최신 닉네임 선택, 남은 티켓 하한, 동기화 큐 상태 및 90일 미조회 길드 제외를 보강했다.
- `pg_cron`과 `pg_net`을 마이그레이션으로 활성화하고 실제 Supabase CLI에서 존재를 확인했다.
- 길드 명단 상태를 `unknown`·`complete`·`limited`로 저장해 미참여 정확도 한계를 UI에 전달했다.
- 니케 사용률을 Day·난이도별로 분리하고 보스 누적딜을 원본 공격 행에서 집계하도록 수정했다.
- 공개 역할은 읽기 전용 분석 데이터만, 운영 테이블과 큐는 `service_role`만 접근하도록 권한과 회귀 테스트를 추가했다.
- 운영자 로그인은 scrypt 비교, HMAC 서명, HttpOnly·SameSite Strict 쿠키, 8시간 만료와 `noindex`를 사용했다.
- 350/400/450MB 단계별 용량 대응과 dry-run, 백업·복원 확인, 명시적 승인, 사후 검증 절차를 문서화했다.
- 자산 URL의 파일명 퍼센트 문자를 이중 인코딩해 jsDelivr에서 실제 이미지가 정상 응답하도록 정리했다.
- 로그인된 BlablaLink에서 읽기 요청 7개를 실행하고 로컬 익명화 JSON을 내려받는 Phase 0 도우미를 추가했다.

## 영향 및 호환성

- 실명단에서 확인된 `bind_area_id=0` 미연동 sentinel은 허용하되 다른 구체 서버 값은 계속 거부한다.
- `member_id`만 회원의 canonical `openid`로 사용하고 닉네임이 같은 과거 공격자를 임의로 합치지 않는다.
- 정산 시즌은 응답 배열 순번을 `source_index`로 보존하고, 진행 시즌은 전체 snapshot을 token 조건 아래 교체한다.
- 새 유니온 등록은 DB advisory lock 아래 분당 5개·24시간 100개로 제한하고 기존 유니온 조회는 계속 허용한다.
- 인증 만료는 `auth_required`, 권한 거부는 `dead`로 분리하며 raw 오류 본문 대신 제한된 오류 코드만 기록한다.
- `npm run session:update`는 일회용 env 파일로 secret을 전달하고 즉시 삭제해 쿠키가 자식 프로세스 명령행에 노출되지 않도록 했으며, 운영 문서에 함수 배포·secret 갱신 절차를 추가했다.

## 영향 및 호환성

- 새 서버 환경변수 `SUPABASE_SERVICE_ROLE_KEY`가 필요하다. 값은 저장소나 클라이언트 번들에 포함하지 않는다.
- Edge Function 이름은 `request-sync`, 요청 본문 계약은 `{area_id:number,guild_id:string}`이다.
- Supabase에는 수집 runtime migration과 `request-sync`·`collect`·`dispatch` 함수 배포가 필요하다.
- 현재 BlablaLink 세션은 본인 유니온만 완전 조회할 수 있으며, 타 유니온은 권한 제한 안내로 종료된다.
- 기존 mock 모드는 공개 Supabase 환경변수가 없을 때 그대로 유지된다.
